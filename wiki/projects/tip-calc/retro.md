## 2026-11-10 — Retro (phases 1–2)

**The one pattern worth acting on:** both phases cleared their gates and then needed two review-and-fix rounds, every round for the same reason: tests that stayed green when the product was broken. Nothing carried the lesson from phase 1 into phase 2.

- **Shipped:** LOCAL-6 shaped the project in the wiki alone: the brief, the "ledger slip" design system, a variants board where the owner picked "Readout first, pinned answer" ([[projects/tip-calc/design/adr-calculator-screen]]), two phases, three ADRs, and a harden pass that fixed 38 findings (eng 21, security 3, design 14) before any code. Phase 1 (LOCAL-11, PR #74) built the whole answer path as a static page: `calc.js` holds the integer-cent rounding and the input rules as one pure function, `index.html` holds the pinned readout, fonts are self-hosted, and a Playwright suite drives the page over `file://` at 320px with the network, storage and WebSockets blocked. Phase 2 (LOCAL-12, PR #76) added the 15 / 18 / 20 presets as a change to `index.html` and its test only; the pressure valve (drop the presets if four cells will not fit) was never needed. LOCAL-13 (PR #75) was a chore ticket that wrote phase 1's build-log line. **Not shipped:** the human-evidence gate (the owner's phone, at a real check). Its two bets, that people accept rounded-up shares and that the keypad works on an iPhone with the readout pinned, are untested ([[projects/tip-calc/plan]] Risk contracts).
- **Trend lines:** no review records exist: `wiki/learnings.md` is still the empty template after four review passes, so the counts below come from the two incident notes ([[notes/2026-11-10-tip-calc-gate-checks-in-one-test]], [[notes/2026-11-10-tip-calc-preset-tests-survived-mutations]]). Harden: 38 findings fixed, with the cross-model reviewer skipped (Codex returned 401), so its "tests 5→9" is a self-score. Phase 1: 10 one-line breaks that the green suite let through (4 in round 1, 6 in round 2) plus one product defect (five extra globals leaked from `calc.js`). Phase 2: 5 breaks (3, then 2) and no product change. The count halved while the rounds stayed at two. I cannot credit the learnings loop for that: nothing was filed, and phase 2 was a one-file change. "Prior learning applied" mentions: none, so nothing has fired and nothing can be retired yet.
- **Patterns:**
  - *Gate green, assertions weak* (phases 1 and 2). The plan wrote its gates as lists of example cases. The breaks that got through were the words around the cases: "in every state" asserted in the first browser context only; "exactly 96px" tested as `>= 96`; "each × people never short" without checking it is an integer; a font "loaded" with no check of which file sits behind it; a box measured where the plan names the text; a state derived from a validator tested only on inputs both agree on (`18`, never `018` or `18.0`); a control tapped once; a row-fit test that measured size, not position.
  - *The lesson stays in a note.* Both notes end with the same rule ("a green gate shows only what its assertions check"). Phase 2's first draft still repeated the class. `learnings.md` is empty, and the feature line's `learn` station is a `pick` with no skill, so nothing writes to it.
  - *Bookkeeping trails the merge.* The build log holds one line, written by the factory after the fact: it is phase 1's goal sentence cut mid-word at 200 characters, with no gate output. Phase 2 has no line. `plan.md` still says "Lock status: pending" and `architecture.md` still describes presets in the future tense. The line's `ship` station is the built-in `land`, not `forge-ship`, so judging by what is on main the build-log, plan and architecture reconcile step never runs.
- **Kept:**
  - The owner's screen choice held: no harden pass edited it, and the build matched it, including a 320 × 208 keypad-up geometry test.
  - Scope held both ways: nothing parked in [[projects/tip-calc/improvements]] leaked into a phase, and each phase's code stayed inside its `Owns` list.
  - Phase 2 wrote its tests first (`ef156ea`, then the feature in `cac4ffc`).
  - Every repair was proved by a break: each new assertion fails on a mutation the old suite passed. That is why the repairs can be trusted.
  - The two incident notes name their root causes plainly.
  - The harden reviewer outage was recorded as "ungraded", not papered over.
  - The environment facts the plan checked (headless shell only; `vm.runInThisContext` needs a function declaration) cost neither build a single environment fix commit.
- **Improve:**
  - Run the break-the-tests pass before review, not inside its fix loop. The feature line's `fix` loop already runs `forge-debug` after a failed review; each of the two review rounds per phase found something a one-line break would have found first. The trial below adds that pass as its own station between `build` and `review`: a worker that makes one-line breaks to the product code for each gate sentence containing "every", "exactly", "only", "no … leaves" or "during the run", adds a case for each break the suite passes, and ends when every break fails.
  - Make `forge-review` append a `learnings.md` line for each finding class it fixes. Its own header says it does; four passes wrote nothing. Two entries ready to file: (1) *rule: test the sentence the plan names, with a break that violates it in the last context, not the first; a box is not its text and a name is not its file.* (2) *rule: for state derived from a validator, test one input the derivation accepts and the validator rejects, and one the validator accepts in a form the derivation may not read; test a control twice.*
  - Have the landing step write the build-log line with the gate output (`fail 0 / cancelled 0 / skipped 0 / todo 0` and the test count) and the full goal, and mark the phase done in `plan.md`. A cut-off goal sentence is not the gate that was met.
- **Subtract (named, not deleted; none is filed in `improvements.md` because this ticket allows `retro.md` only):**
  - **The tip is parsed twice** (phase 2 added the second parse). `calc.js` computes `tipPercent` and returns only cents; `index.html:333-336` re-derives blank, invalid and `Number(trimmed.tip) === preset.percent` to decide which preset is pressed. Caller check: `Number(trimmed.tip)` has one use, and `tipPercent` has no reader outside `calc()`. Two of phase 2's five breaks (the `!tipInvalid` guard, the text compare) and the `018` / `18.0` / ` 20 ` / `0015` cases live in that second parse. Return `tipPercent` from `calc()`: the page presses on `result.tipPercent === preset.percent`, three lines go, and those cases move to `calc.test.mjs`, which needs no browser. The cost is a one-field change to `calc()`'s result shape, which the plan froze at phase 1, and the whole-result `deepStrictEqual` expectations in `calc.test.mjs` (16 `deepStrictEqual` calls, several on the full result). I would do it as a small ticket; it stops being worth it if a consumer I cannot see needs the current shape (the only readers are `index.html` and `calc.test.mjs`).
  - **`wiki/projects/tip-calc/design/.gitkeep`** (0 bytes): the folder now holds four files and a `fonts/` folder, so the placeholder has no job.
  - *Checked and kept:* the wiki copy of the fonts is byte-identical to `tip-calc/fonts/` (`cmp`, all four files) but `specimen.html` and `explore-calculator.html` load it by relative `@font-face`; the two 320 × 208 tests share setup but assert different things (`page.test.mjs:309` overlap, `:579` stacking), so merging saves a context, not a check; `calc.js` has no unused helper.
